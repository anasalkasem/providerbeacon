# ProviderBeacon Security and Synchronization

## Independent team authentication

ProviderBeacon supports first-party staff accounts that do not depend on the Manus OAuth runtime. Passwords are normalized by email and hashed with Node.js `scrypt` using a unique random salt and deliberately expensive parameters. The server never stores or logs plaintext passwords.

The first owner account is created once through `/setup` with `AUTH_BOOTSTRAP_TOKEN`. After one local account exists, the bootstrap endpoint rejects every further setup attempt. New staff members join through expiring, single-use invitation links generated by an owner or authorized administrator.

Successful password authentication creates an opaque random session token. Only its SHA-256 digest is stored in MySQL. The browser receives the raw value in a host-only, HTTP-only, secure, `SameSite=Lax` cookie. Full sessions expire after twelve hours. Accounts are locked for fifteen minutes after five consecutive invalid password attempts.

## Multi-factor authentication

Each staff member can enroll a standards-compatible TOTP authenticator from **Admin → Account security**. The TOTP secret is encrypted at rest with the same vault primitive as provider credentials. Eight one-time recovery codes are generated after successful enrollment; only HMAC hashes of those codes are stored.

When MFA is enabled, password authentication creates only a ten-minute pending session. The session cannot access protected procedures until a valid TOTP or unused recovery code is supplied.

## Provider credential vault

Provider API keys are encrypted with **AES-256-GCM** before they reach the database. Every encrypted value uses a unique 96-bit nonce and purpose-bound additional authenticated data. The key name, provider URL, schedule and a four-character hint can be returned to authorized staff; ciphertext, nonce, authentication tag and plaintext are never returned to the browser.

`VAULT_MASTER_KEY` must decode to exactly 32 bytes and must remain only in the deployment secret manager. Rotating it requires decrypting existing records with the previous key and re-encrypting them with the new key before the old key is removed.

## Scheduled synchronization

The repository contains `.github/workflows/provider-sync.yml`, which runs hourly and can also be started manually. The workflow does not use a stored application secret. Instead, GitHub issues a short-lived OIDC identity token for each run. The application verifies the signed issuer, audience, exact repository, `main` branch, non-empty subject and allowed trigger before processing due integrations. The subject value itself is not parsed because GitHub allows repository-level subject customization.

Provider endpoints are restricted to public HTTPS hosts. DNS is resolved before every call and private, loopback, link-local and metadata-network addresses are rejected. Redirects are disabled. Each integration has an interval, next-run timestamp, lock window, failure count and retry backoff. Imports preserve price history and write success or failure events to the audit log.

## Required production variables

| Variable | Requirement |
|---|---|
| `DATABASE_URL` | MySQL connection string supplied by Railway |
| `RUN_DATABASE_MIGRATIONS` | `true` so pending Drizzle migrations run before the server accepts traffic |
| `VAULT_MASTER_KEY` | Random 32-byte key encoded as base64, base64url or 64 hex characters |
| `AUTH_PEPPER` | Independent high-entropy secret used to hash MFA recovery codes |
| `AUTH_BOOTSTRAP_TOKEN` | One-time high-entropy token used only to create the initial owner |
| `SCHEDULER_OIDC_AUDIENCE` | Optional; defaults to `https://providerbeacon.com` |
| `SCHEDULER_GITHUB_REPOSITORY` | Optional; defaults to `anasalkasem/providerbeacon` |

## Operational runbook

After creating the owner account, enable MFA immediately and store recovery codes offline. Rotate a provider API key by editing its integration and entering only the new key; leaving the field blank preserves the existing encrypted value. Disable an integration before changing its endpoint or when a provider is under review.

Review `auth.*`, `integration.vault.*`, and `integration.schedule.*` events in the audit log. Repeated synchronization failures trigger progressive retry delays but do not expose provider error bodies or credentials to public pages.

## Production verification

On 13 September 2026, the production deployment completed the database migration and started successfully on Railway. GitHub Actions run [`34753695298`](https://github.com/anasalkasem/providerbeacon/actions/runs/34753695298) then obtained a short-lived OIDC token and received a successful response from `https://providerbeacon.com/api/internal/provider-sync`. The response reported `ok: true`, trigger `workflow_dispatch`, and zero integrations due at that moment.

The live authentication and vault verification then completed six checks: owner recovery and RBAC, MFA enrollment, MFA login using a one-time recovery code, invitation registration with auditor least privilege, encrypted credential creation and rotation, and audit-trail validation. The disabled verification integration remains available in the vault as a harmless operational example and is not eligible for scheduled synchronization.
