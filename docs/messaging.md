# Team messaging and customer handoff

The Messages launcher appears on authenticated staff dashboard routes. Staff choose their **receiving language** in the messenger and may independently opt into **Available for customers**. A directory of active employees supports private one-to-one conversations. The public Beacon assistant has an explicit **Talk to an employee** action even when catalogue AI is unavailable; affirmative human requests are also recognized by the assistant planner. Handoff copies the last bounded conversation history and changes the UI to customer support.

## Data and access

Migration `0035_team_messaging` adds preferences, conversations, participants, immutable original messages, translation jobs and one dispatch lock. It does not alter existing account or payment tables. Writes require the canonical Origin; all responses use `Cache-Control: no-store`. Every request rechecks active staff membership. Private employee conversations are visible only to their participants, including when the requester is an owner. Customer conversations are visible to the currently assigned employee and owners/administrators; customers authenticate only their own conversation using a random, HttpOnly, SameSite=Strict cookie. Only its hash is stored. Both the cookie and server authorization expire after 30 days. Expired visits start a fresh session instead of reopening the old conversation. Private query caches are removed when dashboard staff identity changes.

Messages have a server-selected sender and a per-conversation, sender-prefixed idempotency key. Retrying a failed response with the same key does not add another message. Pagination limits a thread response to 50 messages and inbox pages to 60 conversations. Read receipts advance only through a conversation's stored last message; the client records reading only while the thread is visible and at the latest messages. Imported assistant history is explicitly marked and is untrusted context, never evidence of staff actions.

## Availability and handoff

Opted-in staff heartbeat every 30 seconds while the dashboard is visible. A heartbeat older than 90 seconds means unavailable. Auditors can message colleagues but cannot take customer requests. A database dispatch lock serializes routing across replicas; the least-loaded employee is chosen, with oldest assignment time as the tie-breaker. Each employee has at most five open customer conversations. Requests remain honestly marked waiting when nobody is available. Unavailable or suspended assignees return to the queue, checked every 15 seconds. A newly available employee triggers immediate routing. Closing support frees capacity. Owners/administrators may reassign customer conversations; the previous employee then loses access.

## Translation

The existing configured OpenAI Responses integration translates incoming text into the recipient's saved language. It detects the actual language rather than trusting the interface language. Arabic dialect context, neutral Latin American Spanish, negation, obligations and business terminology are covered by explicit interpreter instructions. Numeric values, identifiers, URLs, email addresses and key brand/currency terms are protected and validated after model output. Failed validation is retried and never presented as a successful translation. The immutable original remains available with a toggle; pending and failed translations clearly show the original. Ambiguity can produce a clarification flag.

Translation jobs are durable, have 60-second leases, retry up to three attempts, and recover after a worker crash. The process runs at most two translations concurrently and the database lease prevents duplicate claims. `BEACON_TRANSLATION_DAILY_REQUESTS` defaults to **2000** model requests per day across replicas (valid range 1–10000), separately from catalogue and screening quotas. The existing `OPENAI_API_KEY`, `OPENAI_MODEL`, `BEACON_AI_ENABLED`, `AUTH_PEPPER`, and `PUBLIC_APP_URL` settings are reused. No new integration credential is required. Paid translation does not run in database transactions. Model output, customer text and credentials are never included in application logs. Messages and recent context are sent to OpenAI with `store: false`; the UI discloses processing. This is server-stored messaging, not end-to-end encrypted messaging.

## Load and operations

The open thread polls every three seconds; a minimized staff messenger polls every 12 seconds. Background page polling and heartbeats stop. Staff messenger code is loaded only on dashboard routes. Expired quota buckets are cleaned hourly. Sender, public handoff/IP and translation preparation budgets bound abuse. Existing unread messages and pending jobs survive deployment.

Validation covers both translation directions, original-text controls, refusal/negative handoff intent, queue assignment, capacity, reassignment, suspended/nonparticipant access, guest session isolation, cookie expiration, repeated sends, durable translation failures, atomic budgets, concurrent workers, and pagination. Automated model tests use deterministic responses; they do not establish perfect linguistic accuracy or a live employee-to-customer session.
